# Separately reviewed scoped eligibility

This optional capability assesses a reviewed eligibility rule for a product or
explicit published rate variants. It does not calculate interest, fees, payments,
or total cost and does not assert a bank's acceptance. Mortgage, Savings and TD
share this foundation; financial family adapters remain separate work.

## Identity and private controller

The exact frozen wire and additive SQLite DDL are retained under
`contracts/product_terms/drafts/eligibility-v2/`. The historical draft labels and
literal bytes remain intentional identity-bearing artifacts. The namespace
amendment supersedes the original design's `manifest.files` placement.

`migrate_registry(store, applied_at=...)` explicitly migrates an isolated or
separately authorized evidence store. Opening a store does not apply this
migration. A write transaction encloses legacy row hashing, DDL, foreign-key
checks and the immutable migration receipt. Legacy tables and `user_version=1`
remain unchanged. Large legacy rows or inventories fail before unbounded
materialization. Concurrent initializers verify the same committed DDL identity.

`cdr_terms.executable_registry.stage_subject` and `review_subject` dispatch by
stored wire version. V1 TD subjects retain their exact validator and records;
v2 subjects use `scoped-eligibility-v1` and `product-terms-engine-v8`. Stage and
review compare explicit predecessor identities. New unreviewed successors block
reuse of older approvals. Negative reviews remain possible after source changes.

Positive review requires a separate human or deterministic reviewer, exact
current source/term/document scope, an independently derived benchmark suite,
and the observed preceding review. Verified flags are derived from that record,
never copied from a staged subject or a benchmark's technical selection.
Latest negative review/removal invalidates future current-edition reads. Offline
retained receipts describe their dated adopted edition, not current approval.

Source authority binds finalized capture membership, exact core/details gzip
hashes, the product detail record, and every selected original row/index. A
rate-free product scope also requires the matching raw CDR productCategory.
Six-field revision applicability must match; unknown date precision is not an
unrestricted interval. Reviewed assessment coverage is not an invented bank
offer expiry. Distinct overlapping scopes remain separate candidates; neither
choosing one nor merging their rules proves qualification.

## Local inputs and benchmark proof

Assessment date, amount, security value, purpose, security type and ownership are
scenario roles. They never fall back to profile answers. Customer answers use
subject-specific hashed IDs and effective product provenance. This version has
no derived-LVR adapter; a customer answer must not disguise a missing reviewed
derivation. These private inputs and benchmark artifacts never enter public
assets.

The benchmark gate verifies exact retained code manifests and literal local
dependency closure, plus locked external package metadata. Lock metadata does
not establish which external runtime bytes executed. Actual adapter inputs,
requested targets, all four compressed assets, decoded context and complete
three-valued rule traces are bound and checked. Independent expectations include
meets, does-not-meet, missing information, a distinct holdout, and source-target,
assessment-interval and input-unit refusal controls. The verification oracle is
not a second producer financial engine.

The current app9c6090a technical bridge and source bytes are retained in
`tests/fixtures/executable-templates/eligibility-v2-final-9c6090a.json.gz`.
The earlier966be80 fixture remains unchanged. The later commit preserves the
frozen schema bytes in Git; actual result, asset and code identities are unchanged.
Earlier working vectors remain explicitly in-progress evidence. Controller
composition tests isolate the benchmark seam; a separate test runs the full
actual committed bridge/code/asset gate. Neither constitutes bank approval.

## Optional packaging and compatibility

`build_payload(..., executable_v2_root=...)` explicitly loads current immutable
publications. The default is off. Publication builds require the existing
immutable revision coordinator; encrypted and direct unversioned delivery fail.
No scheduler, deployment configuration or product approval is enabled here.

Descriptors live only in top-level `manifest.executable_v2`, with URL-free
index/shard names, byte counts and hashes. New readers derive the trusted repo's
exact immutable tag URL. The common asset iterator covers validation, copying,
download, upload/readback, recovery, deltas and aggregate budgets. Absent
namespace preserves the old bundle identity. Existing 64 KiB manifest, 4 MiB
details and 8 MiB aggregate transfer limits remain strict; v2 additionally bounds
shards and the expanded snapshot. Quotes are never silently dropped to fit.

The actual shipped eeb20f1 refresh and revision-validator source was exercised
with explicit technical transport/cache/platform stubs: top-level descriptors
cause zero v2 requests while ordinary core/rates adopt successfully. A misplaced
`files` control reproduces the old eager-download failure. This is protocol
compatibility evidence, not APK or native execution acceptance.

Optional `details.displayIdentity` carries exact supplied name/provider and raw
productCategory when bounded nonblank strings exist. Missing metadata stays
absent; consumers retain key fallback. No name or classification is inferred.
The additive reviewed fee-code identity preserves historical pins and records
the actually observed module identity in any future authorized new receipt.
