Jan's 15 October correction replaces 18:00 and 20:00 with **03:00
Australia/Hobart**. The cloud check `6ad0ccf311d881918a8abb6a0c7385bd`
is currently configured for that time, with its first future occurrence on
17 October. It remains diagnostic-only: no equivalent mechanical model-process
deadline has been demonstrated, so it is not eligible as the mutating caller.
This source change does not activate production, enable repair, modify a
scheduler, or grant publication/credential/security authority.

Before runtime activation, commission exactly one mechanically bounded model
caller under a separately approved migration. The concrete bounded option is
the existing Windows launcher: move its trigger, both dispatch-minute checks,
local gate and prompt to 03:00 while preserving its 1,190-second kill-on-close
Job Object and 1,200-second Task Scheduler limit. Pause the competing cloud
repair automation before enabling that sole Windows caller, and verify both
states through their respective supported tools. Retain the original task
definition and every permanent claim; keep older local heartbeats paused.

Prove actual Windows process-tree termination for timeout and launcher death,
including descendants, using harmless native canaries before commissioning.
If the cloud check is retained for diagnosis, it must not dispatch repair or
create another repair model caller. Using it as the sole mutating caller needs
a separately demonstrated platform-enforced model deadline; a policy flag,
receipt or acknowledgement of the missing bound cannot supply containment.
Do not apply the superseded 18:00 patch, create a Pi repair timer, or rely on the
Windows launcher's local-TOML inventory to detect the cloud caller: that
inventory does not include the cloud schedule. No migration occurs in this PR.

03:00 is a check, never permission to interrupt the natural 01:00 ingest.
The static repair service admits at most one claim per Hobart date in
`[03:00,05:00)`, only after both natural/manual ingest units have no main/control
PID or surviving cgroup members and the native lease is absent. Today's daily
unit must have reached successful whole-unit terminal completion after its
main exit. Its existing non-optional post-start `verify_local.py` command and
source SHA are explicitly bound by `pi_daily_repair_admission.py`. The unrelated
deploy-drift monitor is not that post-ingest validation gate. Admission requires
the exact reviewed post-start shell command and its successful execution record
after this run's main exit and before whole-unit inactivity. Installed command
text alone, unexecuted records and records from an earlier run cannot supply
that proof. Actual installed command metadata still requires native acceptance.

Before 03:30, recovery and publication admission additionally require the exact
fixed service cgroup, current invocation and unexpired permanent date claim,
then repeat terminal/validation checks. Other callers retain their 03:30
boundary. Existing native production locking and generation fencing still run
inside the capture child. The daily-repair queue stop hook restores the
dashboard only under its existing started-command/idle-owner proof; ordinary
watchdog restoration retains its 03:30 guard.

The caller must claim its local controller date immediately in the scheduled
03:00 minute and retain the original 20-minute session deadline. If ingest is
active/uncertain, observe read-only within that existing session; attempt no
repair until terminal clearance. If clearance or the minimum execution budget
does not fit, record deferral and finish without a new wake-up, catch-up,
alternate caller, manual retry or claim reset. Failed/ambiguous admitted Pi
attempts permanently consume the date. The Pi service deadline bounds the Pi
process tree, not a remote cloud model process. A 20-minute instruction is not
equivalent containment. Missing mechanical model supervision blocks repair
enablement, independently of passing source tests and the bounded Pi service.

The fixed Pi service retains a 61-second startup limit, 1,100-second runtime,
10-second stop bound, Restart=no, KillMode=control-group and SendSIGKILL=yes.
Queue wait remains one second. The worker retains daily_pass=True, at most
32 logical target probes plus one register probe, a 180-second probe ceiling
reduced to reserve 900 seconds for capture and 45 seconds for cleanup, and the
same hard service deadline. There is no global capture GET-count cap.

Activation requires reviewed merged exact source, full native canary/resource
and consumer acceptance, coherent entry/worker/queue/module pinning, immutable
rollback evidence and specific producer/worker/publication approval. No such
activation is established by these local tests. At the future 17 October

October. Preserve Drive/security/pricing holds and existing observations.
